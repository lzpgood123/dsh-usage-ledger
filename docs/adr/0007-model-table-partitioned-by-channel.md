# 分模型表按渠道分行，跨渠道模型另给一行分组小计

模型身份与渠道无关（见 `CONTEXT.md` 的「模型」），但「分模型」表的聚合键是**渠道 + 模型**（`src/scan.js` 里 `createScanner` 的桶键 `${record.provider}\0${record.model}`），而名称列只渲染 `row.model`。于是同一模型的多条渠道在面板上退化成**同名重复行**——用户没有任何区分手段。这份 ADR 记录为什么保留渠道粒度、以及怎么把它显示清楚。

实测（本机 `$DSH_HOME/sessions`，413 个文件、23541 条记录，2026-09-28）：21 个模型中 3 个跨渠道。`deepseek-v4.1-flash` 的两行分别是 workbuddy 1,375,630,804 tokens / 98.4% 与 trae 723,073 tokens / 0%，名字完全相同。同理 `deepseek-v4-flash` 跨 4 条渠道、`deepseek-v4-pro` 跨 3 条。

**决定**：

① **呈现按渠道拆**——一行仍是「一条渠道上的一个模型」，跨渠道模型的名称列写成 `provider/model`。不新增列：表格已有 10 列，而 #4 的根因正是 min-content（≈837px）超出面板内宽（728px），当时的修法是拆掉 tokens 列那个 76px 硬下限（`src/client.js` 的 `columns` 里那段注释），第 11 列会把风险顶回去；`provider/model` 的写法也已存在于同一面板的未定价提示（`UnpricedNotice`）。

② **跨渠道模型另给一行非交互分组小计**，仅在真正跨渠道时显示（本机 3/21）。单渠道模型的小计与它下面那一行数字完全相同，给了只是噪音与双倍行高。

③ **排序作用于分组**：先按各模型的合计排，组内再按行排。分组因此始终存在，点任何列都不会打散它。

**为什么不直接合并成模型级一行**：`trae 的 deepseek-v4.1-flash 命中 0%` 是真实信息——它说的是这条渠道不复用缓存，是路由决策的输入——合并后这个格子永久丢失。而「某模型整体多少」这个边际量已由分组小计覆盖。

**小计的口径**：命中率与其它行一样是**合计出来的比率**（合计缓存读 ÷ 合计提示词），不是组内各行比率的平均。这个区别在实测数据上极大：deepseek-v4.1-flash 加权 98.4%、直接平均 49.2%，差 49.2 个百分点；deepseek-v4-flash 是 98% 对 73.8%，deepseek-v4-pro 是 72.4% 对 45.6%。

**代价**：名称列变长，窄视口下更早触发截断或换行，加上分组小计又多一行，与 #4 的宽度预算持续相互挤压；「按 tokens 降序」不再全局严格降序，跨组看时数字序会跳；分模型表从此不是「每行一条渠道」的平表，组、小计、分组排序都要在渲染层维护一份。最后一点是刻意的——分组是呈现层的事，payload 不变：改 `aggregate` 的分组键会让 `src/index.js` 的渠道成本累加读到不再唯一的 `row.provider`，渠道表的成本随之算错。

**落地与实测（#9）**：

- 分组在 `src/client.js` 的 `groupModelRows` 里做，`DetailTable` 按行上的 `role: "rollup"` 换一种渲染。`Panel` 另算一份 `modelDetailRows` 交给未定价提示——小计行是合计，混进「未定价占多少 token」的分母会让占比凭空减半。
- 小计行只加类名（`ul-rollup`）与 `<strong>`，**不自己挑颜色或背景**：宿主 token 是硬约束（ADR-0006），而信息已经由前缀、加粗与位置承载；自选背景会改变文字背后的表面色，把 `appearance.test.js` 现成的那批对比度断言变成对旧底色的背书。
- 比率列（`cacheHitRate`）的**组间排序值取小计自己算出的加权值**（`summarizeGroup`），不是组内各行比率的和——后者的量纲没有意义（一行 100% + 一行 0% 会得到 100，压过任何单行的 90%），会让组的次序与它显示的小计自相矛盾。
- 名称列变长的最坏形态进了视口用例：`test/viewport.test.js` 的载荷让 `deepseek-v4.1-flash-thinking-preview` 走两条渠道，于是分模型表同时出现最长的一行（`provider/model`，约 60 字符）与一行小计；四档视口（480/768/900/1400）下面板仍不越界、面板自身也没有横向滚动（窄视口下表格**内部**横向滚动是既定行为，由 `.ul-tablewrap` 承担）。那组用例同时断言小计行与 `provider/model` **确实渲染出来了**——否则量到的是旧布局，「不越界」就成了对旧代码的背书。
- 三条口径都固化成了 `scripts/mutation-check.mjs` 的变异体：`rollup-hitrate-averaged`（加权改成平均）、`rollup-every-model`（单渠道也给小计）、`rollup-ratio-summed`（比率列按和排序）。
