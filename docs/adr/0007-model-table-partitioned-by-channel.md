# 分模型表按渠道分行，跨渠道模型另给一行分组小计

模型身份与渠道无关（见 `CONTEXT.md` 的「模型」），但「分模型」表的聚合键是**渠道 + 模型**（`${record.provider}\0${record.model}`，`src/scan.js:500`），而名称列只渲染 `row.model`（`src/client.js:929`）。于是同一模型的多条渠道在面板上退化成**同名重复行**——用户没有任何区分手段。这份 ADR 记录为什么保留渠道粒度、以及怎么把它显示清楚。

实测（本机 `$DSH_HOME/sessions`，413 个文件、23541 条记录，2026-09-28）：21 个模型中 3 个跨渠道。`deepseek-v4.1-flash` 的两行分别是 workbuddy 1,375,630,804 tokens / 98.4% 与 trae 723,073 tokens / 0%，名字完全相同。同理 `deepseek-v4-flash` 跨 4 条渠道、`deepseek-v4-pro` 跨 3 条。

**决定**：

① **呈现按渠道拆**——一行仍是「一条渠道上的一个模型」，名称列改成 `provider/model`。不新增列：表格已有 10 列，而 #4 的根因正是 min-content（≈837px）超出面板内宽（728px），当时的修法是拆掉 tokens 列那个 76px 硬下限（`src/client.js:821` 的注释），第 11 列会把风险顶回去；`provider/model` 的写法也已存在于同一面板的未定价提示（`src/client.js:640`）。

② **跨渠道模型另给一行非交互分组小计**，仅在真正跨渠道时显示（本机 3/21）。单渠道模型的小计与它下面那一行数字完全相同，给了只是噪音与双倍行高。

③ **排序作用于分组**：先按各模型的合计排，组内再按行排。分组因此始终存在，点任何列都不会打散它。

**为什么不直接合并成模型级一行**：`trae 的 deepseek-v4.1-flash 命中 0%` 是真实信息——它说的是这条渠道不复用缓存，是路由决策的输入——合并后这个格子永久丢失。而「某模型整体多少」这个边际量已由分组小计覆盖。

**小计的口径**：命中率与其它行一样是**合计出来的比率**（合计缓存读 ÷ 合计提示词），不是组内各行比率的平均。这个区别在实测数据上极大：deepseek-v4.1-flash 加权 98.4%、直接平均 49.2%，差 49.2 个百分点；deepseek-v4-flash 是 98% 对 73.8%，deepseek-v4-pro 是 72.4% 对 45.6%。

**代价**：名称列变长，窄视口下更早触发截断或换行，加上分组小计又多一行，与 #4 的宽度预算持续相互挤压；「按 tokens 降序」不再全局严格降序，跨组看时数字序会跳；分模型表从此不是「每行一条渠道」的平表，组、小计、分组排序都要在渲染层维护一份。最后一点是刻意的——分组是呈现层的事，payload 不变：改 `aggregate` 的分组键会让 `src/index.js:188` 的渠道成本累加读到不再唯一的 `row.provider`，渠道表的成本随之算错。
